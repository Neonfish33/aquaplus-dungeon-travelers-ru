# DT2 (PC) — технический отчёт

Всё ниже проверено на `DT2_en.exe` (PC, ENG 1.0, 2 697 728 байт).
Отчёт описывает только сделанное и измеренное.

## 1. Бинарник

- `DT2_en.exe` — PE32 (x86), ImageBase `0x400000`, ASLR выключен
  (DllCharacteristics `0x8100`), 5 секций: `.text` (RVA `0x1000`),
  `.rdata` (`0x198000`), `.data` (`0x27F000`, VirtualSize аномально велик),
  `_RDATA` (`0x40433000`), `.rsrc` (`0x40434000`).
- `dbdata.dll` — DRM/лицензирование (boost.serialization, lm::*), к тексту
  отношения не имеет.
- Импорты: DINPUT8, d3d11, FFmpeg (`av*`, `sw*`), CRIWARE внутри.

## 2. Форматы

### 2.1 PCK (скрипты, шрифтовые архивы)

```
"Filename" + пробелы до 0x14
u32 data_off (смещение таблицы имён относительно +0x18)
имена (NUL-терминированные), смещения u32 от +0x18
"Pack    " + пробелы до 0x14
u32 hsz, u32 count
count × (u32 absolute_offset, u32 size)
данные, выравнивание 0x10
```
Смещения в таблице данных — абсолютные от начала файла.

### 2.2 .fnt (шрифт)

```
0x00: "Table" + пробелы (20 байт)
0x14: u32 texoff
0x18: u32 f1 (размер ячейки: 56 для Font480, 68 для Font600)
0x20: glyph_count × 12 байт: (u32 code, float U, float V)
texoff: "Texture" + пробелы, далее u32 W, u32 H, RGBA8888 (RGB = A)
```
Font480: 3136×672, ячейка 56, 672 глифа. Font600: 3808×816, ячейка 68.

### 2.3 Part-записи (CSpriteParts)

```
u32 count; count × 0x20 байт:
float offsetX, offsetY, advanceX, advanceY, u0, v0, u1, v1
```
Массив адресуется по коду символа; `advanceX` — значение, производное от
ширины английского глифа (174…456 на диалоговом объекте).

## 3. Порт текста

- Источник текста: собственный перевод проекта; Vita-скрипты использовались
  только как технический шаблон структуры PCK, файлы `Script/*.pck`, блобы
  `*.adv.bin`.
- Скрипты PC и Vita отличаются только 8-байтовым заголовком PCK; содержимое
  `adv.bin` совпадает по структуре.
- `tools/port_pc.py`: разбор PC-шаблона (имена/смещения сохраняются),
  подстановка блобов из Vita, пересборка с выравниванием 0x10.
- Результат: 112 файлов; все 112 отличаются от оригинальных PC-скриптов
  (`BattleAI.bin` не изменялся).
- Текст в переводах — транслит-совместимый (см. 4.2).

## 4. Шрифт и коды

### 4.1 Вставка кириллицы

`tools/inject_ru.py`:
- читает `Font1.pck`/`Font2.pck` (исходные — `.orig2`);
- для кодов `0x20..0x7E` затирает ячейку и рисует кириллицу Arial Bold
  (size = `round(f1*0.68)` → 38/46; базовая линия `f1*0.68`);
- пишет только пиксели текстуры; `Table` (коды/UV) не меняется.

### 4.2 Маппинг кодов (транслит)

```
а a  б b  ц c  д d  е e  ф f  г g  ч h  и i  ж j  к k  л l  м m  н n
о o  п p  я q  р r  с s  т t  ю u  в v  ш w  х x  у y  з z
ы #  й =  ь }  э &  щ {  ъ |  Э >
```
Служебные маркеры `<C1>`, `<C9>` в тексте не перекодируются.

## 5. Движок текста (найденные адреса)

Классы (RTTI): `Utility::CSpriteParts`, `String::CString`,
`String::CStringBase`, `String::CStringCursor`, `String::CLineCursor`.

| Что | Адрес |
|---|---|
| vtable `CSpriteParts` | `0x65C280` |
| vtable `CStringBase` | `0x6506AC` |
| vtable `CStringCursor` | `0x6506D0` |
| ctor `CSpriteParts` | `0x51B080` |
| load `CSpriteParts` (Parts/Texture) | `0x51B480` |
| advance X / Y | `0x51B370` / `0x51B390` |
| `CFont::parse` (Table/Texture) | `0x4477A0` |
| `FindGlyph` | `0x447950` |
| draw `CStringBase` | `0x4632C0` |
| draw `CStringCursor` | `0x465940` |

`FindGlyph` (thiscall): `ecx` = объект CFont, аргументы на стеке:
`[esp+4]` out-вершинный буфер, `[esp+8]` код, `[esp+0xC]` x, `[esp+0x10]` y,
`[esp+0x14]` цвет, `[esp+0x18]` sx, `[esp+0x1C]` sy.
Пролог (10 байт): `mov edx,[esp+8]` / `sub esp,8` / `xor eax,eax` / `push ebx`
(`0x447950..0x447959`), продолжение с `0x44795A`.

`CFont` поля: `+0x8` cell, `+0xC` cell, `+0x10` число глифов, `+0x14`
указатель на записи (code,U,V).

## 6. Причина дефекта

Шаг строки берётся из метрики **английского** шрифта, а не из нашего атласа.
Отсюда: узкие кириллические буквы получали шаг больше нужного, широкие —
меньше, что давало одновременно «наезд» и разреженность. Проверено: при
одинаковом `advanceX=392` наблюдались разные шаги у разных кодов, т.е. шаг
следует за исходной таблицей английских глифов.

## 7. Статический патч exe

`tools/patch_static.py` (никаких DLL):

1. В exe добавляется секция `.rufix` (RVA `0x4043A000`, raw в конец файла,
   характеристики `0xE0000060` — RWX, `SizeOfImage` увеличивается).
2. По адресу `0x447950` записывается `E9 rel32` на заглушку.
3. Заглушка (94 байта, ручная сборка):
   - сохраняет регистры (`pushad`);
   - читает `code/x/y` из стека;
   - если `y` изменился **или** `x <= lastX` — новый кадр/строка:
     `cursor = x`;
   - пишет в стек новый `x = cursor`;
   - `cursor += width[code & 0xFF]`;
   - выполняет украденный пролог (`mov edx,[esp+8]`, `sub esp,8`,
     `xor eax,eax`, `push ebx`) и прыгает на `0x44795A`.
4. Таблица `width[256]` — байты, вычислена из нашего атласа:
   `round(ink*1.2)+2`, минимумы для `. , : ; ! ?` = 12, `-` = 14,
   кавычки 9–11, скобки 12, пробел = 14.

Состояние (cursor/lastX/y) лежит в той же секции.

## 8. Проверка

- Игра запускается с пропатченным exe без `dinput8.dll` и `.asi`.
- Диалоги: текст ровный, буквы не слипаются, строки в рамке
  («Меня зовут Фрид Эйнхард…», «Я положил книгу…», «Если ты слышал меня…»).
- Прогон ~10 минут без вылетов.

## 9. Что не сделано (факт)

- Имена в плашках (`Chief`, `Fried`) — другой источник, не переведены.
- `Data\ENG\Parameter` (меню, предметы, навыки) — не переведены.
- Перенос длинных строк считает движок по старым метрикам: текст остаётся
  в рамке, но место переноса может быть неоптимальным.
- Vita-порт (изображения/TEX, full/half-width) не затрагивался.
