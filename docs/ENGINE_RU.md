# Dungeon Travelers 2 (PC) — полный отчёт по реверсу движка

Документ собирает всё, что было дизассемблировано, декомпилировано и проверено
на живой игре. Только факты и измерения; спорные места помечены как «наблюдение».

Цель работ: русский текст в PC-версии 1.0 и устранение «наезда» букв.

---

## 1. Среда и бинарники

- Игра: `DT2_en.exe`, PE32 (x86), 2 697 728 байт, ImageBase `0x400000`,
  ASLR выключен (`DllCharacteristics = 0x8100`).
- Секции:

| Секция | RVA | VirtualSize | Raw | Флаги |
|---|---|---|---|---|
| `.text` | `0x1000` | `0x19639D` | `0x400` | `0x60000020` R-X |
| `.rdata` | `0x198000` | `0xE6D08` | `0x196800` | `0xC0000040` R/W |
| `.data` | `0x27F000` | `0x401B3C74` (аномалия) | `0x27D600` | `0xC0000040` R/W |
| `_RDATA` | `0x40433000` | `0x5E0` | `0x28D000` | `0x40000040` R |
| `.rsrc` | `0x40434000` | `0x5318` | `0x28D600` | `0x40000040` R |

Аномально большой `VirtualSize` у `.data` — особенность сборки; при статическом
патче это учтено (см. §10).

- Импорты: `DINPUT8.dll`, `d3d11.dll`, `dbghelp.dll`, `IMM32`, `WINMM`,
  `XINPUT1_3`, FFmpeg (`avformat-58`, `avcodec-58`, `avutil-56`, `swscale-5`,
  `avfilter-7`).
- `dbdata.dll` — лицензирование/DRM (173 экспорта, `boost::archive`,
  `lm::License`, `HardwareBinding`, `MacInfo`), к рендеру текста не относится.
- Внутри exe — CRIWARE (ADX/Sofdec), DirectX 11.

Инструменты: Ghidra 12.1.4 (headless через `rea-agents`), capstone, pefile,
Python; рантайм — DLL-хуки + `ReadProcessMemory`/`WriteProcessMemory`,
позже статический патч PE.

## 2. Контейнеры и ресурсы

### 2.1 PCK (скрипты, шрифты, часть данных)

```
0x00  "Filename" + пробелы до 0x14
0x14  u32 data_off        ; смещение таблицы имён относительно 0x18
0x18  таблица имён: count × u32 offset, затем имена (NUL-terminated)
       "Pack    " + пробелы до 0x14
       u32 hsz, u32 count
       count × (u32 absolute_offset, u32 size)
       данные с выравниванием 0x10
```

- Смещения в таблице данных **абсолютные** от начала файла.
- Vita-вариант отличается только 8-байтовым магическим заголовком; внутренние
  блобы `*.adv.bin` совпадают по структуре — на этом построен порт.

### 2.2 Шрифт `.fnt` (внутри `Font1.pck` / `Font2.pck`)

```
0x00  "Table" + пробелы (20 байт)
0x14  u32 texoff
0x18  u32 f1        ; размер ячейки атласа
0x20  glyph_count × 12 байт: (u32 code, float U, float V)
texoff: "Texture" + пробелы
        u32 packed W|H<<16, затем RGBA8888
```

- Формат пикселей: 4 байта на точку, **RGB = A** (используется альфа-канал).
- `Font480`: 3136×672, `f1 = 56`, 672 глифа, сетка 56×12.
- `Font600`: 3808×816, `f1 = 68`, 672 глифа (для крупного текста).
- `Font483`/`Font603`: 491/495 глифов (CJK), `Debug.fnt`: 93 глифа.
- Чанка `Parts` в файлах шрифтов нет.

### 2.3 Метрики `CSpriteParts` (`Parts`)

```
u32 count
count × 0x20 байт:
    float offsetX, offsetY, advanceX, advanceY, u0, v0, u1, v1
```

Массив индексируется **кодом символа**. Поле `advanceX` у диалогового
объекта — 174…456 (ширина оригинальных английских глифов). Важно: имя поля не
означает, что движок использует его как шаг текста — проверка маркерами в
памяти (см. §14) показала, что шаг от него не зависит.

### 2.4 Текстуры (для полноты картины)

- `.tex` — контейнер с 20-байтовым заголовком, далее PNG либо LZ77 + палитра;
  формат отличается между PC- и Vita-версиями.
- `.ptx` — `PTX@`, `u16 w` по +6, `u16 h` по +8 (480×480, 368×367).
- `.ptg` — `PTG2`; `.ptp` — `PTP\0`.

## 3. Классы движка (RTTI)

Найдены строки RTTI и восстановлены vtable:

- `Utility::CSpriteParts` — спрайт/«части» (метрики, UI, плашки).
- `String::CString` → `String::CStringBase` → `String::CStringCursor`,
  `String::CLineCursor` — подсистема текста.

### 3.1 `CSpriteParts`

vtable `0x65C280`:

| Слот | Адрес | Назначение |
|---|---|---|
| +0x00 | `0x51B190` | деструктор |
| +0x04 | `0x4475E0` | getter базового размера (`[this+8]`) |
| +0x08 | `0x51B2E0` | draw (квад спрайта) |
| +0x0C | `0x51B370` | advance X = `[[this+0xC]+code*0x20+8]` |
| +0x10 | `0x51B390` | advance Y = `+0x0C` |
| +0x14 | `0x51B480` | load: ищет `Texture`, `Parts`, `Anime` |
| +0x18 | `0x671C9C` | RTTI |
| +0x1C | `0x51B690` | — |
| +0x20 | `0x671D24` | RTTI |
| +0x24 | `0x51BA70` | — |
| +0x28 | `0x4F5490` | — |
| +0x2C | `0x51BBB0` | — |

Конструктор `0x51B080` обнуляет `+8/+C`, вызывает `0x42AF50` (kstring) и
`0x51B480`. Загрузчик `0x51B480`:
- находит `Texture` → `[this+4]`;
- `Parts` найден → `[this+8] = count`, `[this+0xC] = массив`;
- иначе `count = 1`, значения по умолчанию из размеров текстуры.

### 3.2 Текст: `CStringBase` / `CStringCursor`

`CStringBase` vtable `0x6506AC`: `+0x00 0x4631D0`, `+0x04 0x463290`,
`+0x08 0x4632C0` (draw), `+0x0C 0x4639A0`, `+0x10 0x464190`,
`+0x14 0x464150`, `+0x18 0x4641F0` (обнуление структуры символа),
`+0x1C 0x4641C0` (цикл по символам), `+0x20 0x66CEB0`, `+0x24 0x465300`.

`CStringCursor` vtable `0x6506D0`: `+0x00 0x465300`, `+0x04 0x463290`,
`+0x08 0x465410`, `+0x0C 0x4654A0`, `+0x10 0x4654E0`, `+0x14 0x464150`,
`+0x18 0x4641F0`, `+0x1C 0x4641C0`, `+0x20 0x66CF28`, `+0x24 0x4658E0`.

Конструкторы:
- `CStringBase` — `0x4630B0`: `[+0xC] = param_4*0x23/10` (макс. символов),
  `[+0x10]` — число строк, `[+0x24]` — массив указателей на записи символов
  размером `([+0xC]+1) << 5` (0x20 на символ).
- `CString` — `0x4665F0` (вызывает базовый).
- `CStringCursor` — `0x465230`/`0x465233`: поля `+0x54…+0x64`
  (флаги/цвет/ширина), создаёт `CLineCursor` через `0x461500`.

Структура символа (0x20 байт), как её читает draw:
`+0x00 X`, `+0x04 Y`, `+0x08` (доп.), `+0x0C` флаг, `+0x10` код символа,
`+0x14` цвет/атрибуты, `+0x1C` флаг.

### 3.3 Отрисовка текста

- `CStringBase::draw` — `0x4632C0`; `CStringCursor::draw` — `0x465940`.
- Сначала берётся базовый размер `base = [CFont+8]` (`0x4475E0`).
- Затем `FUN_004642D0` возвращает коэффициент из таблицы
  `60/48/44/40/36/32` (зависит от текущего режима/масштаба).
- На каждый символ:
  - если код `< 0x7D0` — шрифт `[0x6E5984]`, иначе `[0x6E59D0]`
    (см. `0x464FF0`); при кодах ≥ 2000 индекс = `code - 2000`;
  - вызов `FindGlyph(font, code, x, y, color, sx, sy)` (`0x447950`);
  - шаг по X вычисляется в коде раскладки (`0x4634xx`/`0x465940`); поле
    `advanceX` из `CSpriteParts` на него не влияет (проверено маркерами, §14);
  - `FindGlyph` применяет к x смещение `pen = max(0, base - adv) * ratio`,
    где `advanceX` используется как «посадочная» метрика глифа.

Смещение по X в `FindGlyph`: `x = charX + origin + pen`.
Именно поэтому перехват `FindGlyph` позволяет полностью управлять
горизонтальной раскладкой.

## 4. `FindGlyph` — центральная функция текста

Адрес `0x447950`, thiscall: `ecx` = объект `CFont`.

Аргументы на стеке:

| Смещение | Аргумент |
|---|---|
| `[esp+4]` | указатель на выходной вершинный буфер |
| `[esp+8]` | код символа |
| `[esp+0xC]` | x (int) |
| `[esp+0x10]` | y (int) |
| `[esp+0x14]` | цвет |
| `[esp+0x18]` | sx |
| `[esp+0x1C]` | sy |

Пролог (10 байт, `0x447950…0x447959`):

```
8B 54 24 08   mov  edx,[esp+8]
83 EC 08      sub  esp,8
33 C0         xor  eax,eax
53            push ebx
```

Продолжение — `0x44795A` (`mov ebx,ecx; push esi; push edi; …`).
Эти 10 байт обязательно надо выполнить при перехвате (иначе `edx` и стек
ломаются — на этом падала первая версия статического патча).

Что делает функция:
- ищет код в таблице глифов `[CFont+0x14]` (записи по 12 байт: code, U, V),
  количество — `[CFont+0x10]`;
- строит 4 вершины квада размером `cell * sx` по X и `cell * sy` по Y,
  где `cell = [CFont+0xC]`;
- UV вершины: `u = entry.u`, `v = entry.v`, плюс поправки
  `[CFont+0x18]` / `[CFont+0x1C]` (доля ячейки в атласе);
- пишет координаты и UV в выходной буфер.

Поля `CFont`:

| Смещение | Значение |
|---|---|
| `+0x04` | объект текстуры |
| `+0x08` | cell (продублировано с +0x0C) |
| `+0x0C` | cell |
| `+0x10` | число глифов |
| `+0x14` | массив записей (code,U,V) |
| `+0x18` | `cell / textureW` |
| `+0x1C` | `cell / textureH` |
| `+0x20` | флаг «первый код < 0x80» |

Парсер `CFont` — `0x4477A0` (находит `Texture` через `0x447B30`, затем
`Table`; копирует записи).

## 7. Причина дефекта шага

Наблюдения:
- Поле `advanceX` для кодов берётся из таблицы английского шрифта:
  например `'o'`=230, `'w'`=174, `'u'`=392, `'l'`=286, `'H'`=224,
  пробел=456 (объект диалога, 161 запись).
- Попытка вывести шаг из `advanceX` (линейная модель `step ≈ base − adv*ratio`)
  даёт лишь частичное совпадение, а при одинаковом `advanceX=392` шаг отличался
  (31…32), при `174` — 34 и 45.
- Решающая проверка: маркеры 999/888, записанные в `advanceX` обеих таблиц,
  игра загрузила в память, но шаги не изменились (space 18, `e` 31, `i` 12).
  Значит шаг считается в коде раскладки, а `CSpriteParts` — не источник шага.

Итог: наши глифы шире английских, а шаг остаётся «английским» → узкие буквы
разъезжаются, широкие слипаются. Равномерный масштаб X (1.35/1.5) проблему не
решает: он растягивает всё подряд.

## 8. Рантайм-инструментарий (использовался при реверсе)

- ASI-загрузчик: `dinput8.dll` (Ultimate ASI Loader x86), игра импортирует
  `DINPUT8`, поэтому `.asi` подхватывается автоматически.
- `hookfont.asi` — DLL с inline-хуком `FindGlyph` (перехват 10 байт пролога)
  и vtable-хуками `CSpriteParts`.
- Инжект в живой процесс — `injector.exe` (`VirtualAllocEx` +
  `CreateRemoteThread(LoadLibraryA)`), 32-бит.
- Диагностика: запись позиций глифов в статический буфер прямо из хука
  (вызов C-функций из naked-хука недопустим — падение), затем дамп из
  отдельного потока.
- Чтение объектов: `[0x6E5984]` (952 записи) и `[0x6E59D0]` (161 запись);
  массив метрик — `[obj+0xC]`, запись 0x20.
- `WriteProcessMemory` работает, но значения перезагружаются движком —
  поэтому фикс сделан на уровне кода/данных, а не памяти.

## 9. Итоговый фикс (в поставке)

Статический патч `tools/patch_static.py`, без DLL:

1. Добавляется секция `.rufix` (RVA `0x4043A000`, raw в конец файла,
   флаги `0xE0000060` RWX), `SizeOfImage` увеличивается.
2. В `0x447950` пишется `E9 rel32` на заглушку.
3. Заглушка (94 байта, ручная сборка, состояние в той же секции):
   - `pushad`, чтение `code/x/y` из стека;
   - если `y` изменился **или** `x <= lastX` → новый кадр/строка:
     `cursor = x`;
   - `x = cursor` записывается обратно в стек;
   - `cursor += width[code & 0xFF]`;
   - выполняется украденный пролог и `jmp 0x44795A`.
4. Таблица `width[256]` (байты): `round(ink*1.2)+2` по атласу Font480,
   минимумы: `. , : ; ! ?` = 12, `-` = 14, кавычки 9…11, скобки 12,
   пробел = 14.

Кадр определяется по `x <= lastX`, потому что движок перерисовывает строку
каждый кадр с теми же координатами; без сброса курсор уходил бы вправо
бесконечно (это проверено экспериментально).

## 10. Проверка

- Запуск пропатченного exe без `dinput8.dll` и `.asi` — работает.
- Диалоги: ровный шаг, текст в рамке:
  «Меня зовут Фрид Эйнхард…», «Я положил книгу, которую держал в руке…»,
  «Если ты слышал меня, то мог бы хотя бы ответить мне!».
- Прогон ~10 минут без вылетов.
- Неудачные варианты и их причины (для истории): вызов C-функции из
  naked-хука → crash; запись в «нулевые окна» `.rdata`/`.data` → порча данных
  (0xC0000139); секция по «дикому» RVA `.rsrc` → промах адреса; пропуск
  украденного пролога `FindGlyph` → `edx` мусор и падение на `0x4479D4`.

## 11. Ограничения (факты)

- Имена в плашках (`Chief`, `Fried`) — отдельный источник, не переведены.
- `Data\ENG\Parameter` (меню, предметы, навыки) — не переведены.
- Перенос длинных строк считает движок по старым метрикам: текст остаётся
  в рамке, но точка переноса может быть неоптимальной.
- Патч привязан к адресам конкретной сборки (`DT2_en.exe` 2 697 728 байт).
- Vita-часть (TEX-форматы, full/half-width ограничения) не затрагивалась.

## 14. Метрики шрифта: что проверено (обновление)

- Выбор шрифта по коду — `0x464FF0`: коды `< 0x7D0` -> объект `[0x6E5984]`
  (952 записи, таблица `Parts` из `Data\ENG\UI.tex`), коды `>= 0x7D0` ->
  `[0x6E59D0]` (161 запись, `Parts` из `Data\ENG\UI2.tex`).
- `0x51B370` (advX) = `fld [[this+0xC] + code*32 + 8]`; `0x51B390` (advY) —
  поле `+0xC`. Обёртки: `0x464F70` (advX по коду), `0x464FB0` (advY).
- Поле `+8` **не является advance**: после записи маркеров 999/888 в оба файла
  движок их загрузил (проверено чтением памяти процесса), но шаги остались
  прежними (space 18, `e` 31, `i` 12). Значит шаг считается в коде раскладки
  (`0x4634xx` / `0x465940`), а не берётся из этих таблиц.
- Реальные шаги движка (лог `FindGlyph`, чистый exe): space 18, `i`/`l` 11,
  `t` 22.5, `e` 31, `o` 32, `w` 45.
- Практический вывод: ширины задаёт стаб патча (`.rufix`); переносы строк в
  переводе ручные, поэтому метрики движка на разбивку не влияют.
